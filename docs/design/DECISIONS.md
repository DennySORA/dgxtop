# dgxtop v2 rewrite — implementation decisions

These decisions refine `spec/dgxtop-v2/` where the specification leaves a choice open. The
specification files themselves are sealed by `spec/dgxtop-v2/MANIFEST.json` and are not edited;
decisions that would change spec semantics are not taken here.

| ID | Decision | Reason / alternatives | Spec refs |
|---|---|---|---|
| D-01 | UI strings and process records are English. | The previous session recorded "This project uses English" at the user's request; spec label examples are Traditional Chinese only because the spec is written in Chinese. The semantics (text, not colour; "unsupported"/"read failed"/"source conflict") are kept. | UI.md §2, ARCHITECTURE §9 |
| D-02 | The spec package lives in the repository at `spec/dgxtop-v2/` (byte-identical; 79 files verified against MANIFEST). | The spec README asks for this path; contract tests and `include_str!` of `examples/config.default.json` (single default source) depend on it. | README.md, CONFIG.md |
| D-03 | Process records do not use catalog entries. A process is the entity `process:<pid_ns>:<pid>:<start_ticks>`; the sanitized command basename travels in `provenance.channel`, `/proc/<pid>` in `provenance.device_path`, and the numeric owner in a `process.uid` record (raw static metric added to the core catalog). | Processes churn every second; catalog paging for them would cost more than the records. No full command line is ever read or stored. | METRICS.md, SECURITY.md §5 |
| D-04 | Read groups with more than 256 records are paged: page `n` is requested with read group `<group>:<n>`; non-final pages return `status: partial` + `error_code: PAGE_CONTINUES`; a page-0 request takes a fresh snapshot that later pages slice. The Manager accumulates pages of one cycle before running a collector. | Keeps the 256-record / 1 MiB frame limits without a schema change. | INTERFACES §10, RUNTIME §3 |
| D-05 | Replay adapters (`replay`, `replay-N`) spell read groups `<live adapter>.<group>` (e.g. `hwmon.fast`) and are routed to the same collectors as the live group; their samples are `replay`/`simulated` and only enter canonical state when the policy namespace is replay (`--replay`). | Lets REF benchmarks drive the real collectors without mixing namespaces. | ADR08, OPERATIONS §2 |
| D-06 | `UpdateViewSession` fields keep the schema shape; semantics depend on `view`: processes = selected ProcessKey + GPU filter (`selected_entity_id`) + name filter; gpu_detail = GPU entity; history/sources = series selector `metric_id|scope|entity_id` + window token (`5m`,`1h`,`6h`,`12h`,`24h`) or text filter. | No new command fields (closed schema). | command.schema.json, UI.md §3 |
| D-07 | `Config::effective_command_bytes()` caps a command at 64 KiB, reduced (never exceeded) when the reserve partition cannot hold commands x 64 KiB beside archive + log + bookkeeping; validation fails below 8 KiB per command. `queues.ingress_bytes` must fit the scaled ingress partition. | CONFIG.md asks to limit the per-command cap rather than overcommit. | CONFIG.md, RUNTIME §6 |
| D-08 | Arbitration tolerance for non-temperature gauges defaults to 10 % of magnitude (engineering default, not a sensor truth); temperatures use `quality.temperature_disagreement_deg_c`. | The spec only fixes the CPU temperature example. | ARCHITECTURE §5.4 |
| D-09 | `RawKind::Static` values (max frequency, power limit, framebuffer total) carry their real read time and use the discovery interval (`<adapter>/discovery`) for freshness. | Static metadata is read at discovery, not every cycle; re-sending it with fake fresh timestamps would misrepresent freshness. | RUNTIME §3 |
| D-10 | GB10 (DGX Spark) hwmon labels `cpu_p`/`cpu_e` map to `cpu.power.cluster`; `cpu.power.package` is then a *derived* value (formula: sum of both, both source ids listed). `soc_pkg` maps to `cpu.power.platform`. Quality is `usable`, not `verified`, until checked on real hardware. | Keeps the legacy Spark CPU power feature without presenting an unverified mapping as verified. | METRICS.md, ARCHITECTURE §5.2 |
| D-11 | NVML PCIe throughput is reported with native unit `KB_unverified_per_second`, which has no conversion; collectors publish it as unavailable (`UNIT_UNVERIFIED`) until a verified profile exists. `gpu.memory.bandwidth.estimated` is not produced (no validated model). | "KB vs KiB must not be guessed"; no busy%-times-peak bandwidth. | METRICS.md |
| D-12 | Host identity is `host-` + the first 16 hex characters of SHA-256(machine-id); the raw machine-id is never exposed. | machine-id should not leak into logs/exports. | SECURITY §5 |
| D-13 | Release artifacts are GNU x86_64 and aarch64 only; no musl artifacts, no installer fallback. GitHub Actions are pinned by commit SHA; CI uses toolchain 1.92.0. | OPERATIONS §4–5. | OPERATIONS.md |
| D-14 | Integration suites live in `tests/<suite>/main.rs` and benches in `benches/<name>/main.rs`, registered as targets of the `dgxtop` package so they may assemble several concrete crates without production dependency edges. | IMPLEMENTATION_LAYOUT.md layout with a virtual workspace. | IMPLEMENTATION_LAYOUT.md |
| D-15 | Terminal hang-up is detected by a runtime `TtyInputGate` (poll(2) on a close-on-exec duplicate of the terminal: stdin when it is a TTY, otherwise `/dev/tty`). The TUI enters crossterm's reader only right after the gate saw the terminal alive; `POLLHUP`/`POLLERR`/`POLLNVAL` end the loop with exit reason `InputClosed` (shutdown reason "terminal hung up", no restore bytes written, exit status 0 like `OutputClosed`). When crossterm leaves bytes unread (its epoll is edge-triggered), the gate waits only for a hang-up instead of reporting the same bytes again. | crossterm 0.29 retries end-of-file reads forever (`event/source/unix/mio.rs`), so a closed PTY master pinned the UI thread at 100 % CPU and the process never exited. Reading and parsing input without crossterm was rejected as a much larger change. | UI.md §5, AT26, AT39 |
| D-16 | After a termination signal the existing signal-watcher thread waits at most 5 s for the frontend; if it is still running (the residual window between the gate check and crossterm's read), it logs, restores the terminal best effort and exits with status 1. | AT39 forbids unbounded waits; reusing the signal thread keeps the RUNTIME §1 thread budget. | RUNTIME.md §1, §8, AT39 |
| D-17 | Terminal descriptors duplicated by the runtime (`NonBlockingTerminal`, `TtyInputGate`) are close-on-exec. | Adapter hosts restarted later must not inherit the user's terminal. | RUNTIME.md §1, SECURITY.md |
| D-18 | Unconfirmed action endings are audited as their own `action_attempts` rows: a timer expiry or a policy revocation gets a fresh request id whose detail names the prepare request; a refused confirmation (including an unknown token or another session) is recorded under its own request id; a definitively refused intent is recorded as an attempt, never as an outcome of an intent row that does not exist (an uncertain commit keeps its closing `not_sent` outcome). | `action_attempts.request_id` is a primary key, so reusing the prepare's id made the store drop the ending as a duplicate; audit.sql keeps refusals without intents in this table. | SECURITY.md §3, audit.sql, AT10, AT32 |
| D-19 | Fail-stop: the Manager control thread and the hot-store actor run under `FailStop::guard` (`catch_unwind` at the thread boundary). A panic halts process-action sends (the action worker refuses with `NotSent`), requests shutdown and makes the process exit with status 1 and `fail-stop: <reason>`. The Manager's `Drop` marks every session as shutting down, so a frontend never keeps drawing a dead Manager. | SPEC.md §7: unrecoverable Manager/HotStore invariant errors stop, revoke actions and restore the terminal instead of signalling with unknown state. Driver aborts and OOM stay outside what `catch_unwind` can catch. | SPEC.md §7, AT39 |
| D-20 | The verified identity carries the raw command name (at most 64 bytes); displays sanitize it, and the audit store keeps `audit_command_name`: an absolute path is reduced to its last component (never a full path on disk), kernel names keep their slashes (`kworker/0:1H`), control and bidi characters become `\u{..}` and a backslash `\\`. | INTERFACES.md §1: displays strip control codes while the Store keeps a bounded, auditable escaped form; the old path split also cut kernel thread names. | INTERFACES.md §1, SECURITY.md §5, AT17 |
| D-21 | A projection reserves `runtime.max_projection_bytes` before it is built and shrinks the permit to the measured size afterwards; a frame the ledger cannot admit is skipped before building. | AT21: the peak may not be allocated first and checked afterwards. The configuration already guarantees sessions x 2 x the cap fit the presentation partition. | RUNTIME.md §6, AT21, AT25 |
| D-22 | Each snapshot entry carries its stale deadline (`sample time + stale_factor x source period`, the period being the larger of the read-group period and the source update interval); the projection shows a value at or past that deadline as stale and keeps the old reading only as last good. | A hung backend commits nothing, so a commit-time verdict stayed "ok" with a growing age. `CanonicalSample` is a closed schema, so the deadline lives on the internal snapshot entry. | STORAGE.md §3, AT04, AT24 |
| D-23 | The archive worker reports each journal's fate to the Manager (`ControlCompletion::Archive`: committed, or a gap caused by a busy worker or a failed write, plus the archive partition status). The Manager counts gaps in `archive_gap_total` by bounded cause and shows the archive status as a banner. | STORAGE.md §1 separates memory_committed / archive_pending / archive_committed / archive_gap, and ARCHITECTURE §7 requires a visible degraded state; dropped journals used to be logged only. | STORAGE.md §1, ARCHITECTURE.md §7, AT06 |
| D-24 | Shutdown uses one 3 s deadline for all application-controlled waits together (Manager join, worker stops, adapter hosts), 250 ms of it reserved for the final log flush. | RUNTIME.md §8 bounds the waits together; the stages used to get 3 s each (about 10 s worst case). | RUNTIME.md §8, AT39 |
| D-25 | An uncertain persistent commit stays recognizable in the closed command-result schema through the `(commit_uncertain)` marker that `CommandResult::from_error` guarantees in the message; the UI reports such results as "outcome uncertain" (naming the adopted on-disk revision when known), never as "not changed". | INTERFACES.md §9 adds `commit_uncertain` to error details, but `command-result.schema.json` has no field for it. | INTERFACES.md §9, CONFIG.md, AT36 |
| D-26 | When the selected process is no longer in the process table (it exited), the processes view reports `selected_missing` and the status line says its values are unavailable; a selection merely hidden by a filter is not reported. | AT09: an exited process is marked unavailable instead of disappearing silently. | METRICS.md (process cardinality), AT09, AT13 |
| D-27 | REF replay hosts serve live adapter families. `ReplayFixture::slice(index, count)` gives each live adapter family (read-group prefix, in sorted order) to host `ordinal mod count`, together with the family's sources, their samples in every cycle, the faults of its groups (faults without a group go to every slice) and the entities its sources reference plus their ancestors (unreferenced entities go to slice 0). The REF bench writes one slice file per host, so each host decodes only its own part. | PERFORMANCE.md §1 fixes 7 resident hosts, one per live adapter. Every host used to decode the whole 2048-source fixture and drop most of it, so the CPU budget measured parsing that a live adapter never does. A per-source round robin would split one family over several hosts and change what a collector sees in one cycle. | PERFORMANCE.md §1, D-05 |
| D-28 | The REF generator's `sources` counts every catalog source: key sources = `sources − row sources` (REF: 2029 key sources + 19 process row sources = 2048). | PERFORMANCE.md §1 fixes 2048 sources. The generator used to add the row sources on top (2067 sources). | PERFORMANCE.md §1, RUNTIME.md §5 |
| D-29 | Sampling phases are per adapter: `phase = stable hash(adapter id) mod period`. The groups of one adapter share its slot (a period that is a multiple of a shorter one lands on the shorter one's slots), while different adapters stay spread over the period. A collector's idle backlog waits at most 25 ms while a host that contributed to it still has a read in flight, so the groups of one host cycle feed one collector run. | RUNTIME.md §3 spreads the initial phase per adapter. Per-group phases scattered one host's groups over the second, so the GPU collector ran once per group (about 2.2 runs/s) instead of once per cycle. PERFORMANCE.md §4 lists read-group merging. The 25 ms bound keeps a slow or hung host's data within the latest-data budget. | RUNTIME.md §3, PERFORMANCE.md §2, §4 |
| D-30 | In the normal state, projections follow data changes with a minimum spacing of 50 ms (or the frame interval if that is shorter); the viewer still renders at most `ui.fps` frames per second from its latest-only slot. Outside the normal state, projections follow the reduced frame interval. | PERFORMANCE.md §2 measures Adapter read_finished → published revision (p95 ≤ 100 ms), queueing included. Tied to the 4 fps render cap, a change could wait up to 250 ms. UI.md §4 already decouples rendering from publishing. | PERFORMANCE.md §2, UI.md §4, RUNTIME.md §7 |
| D-31 | Hot-path representation without wire changes: collector candidates and snapshot entries are shared `Arc`s; identity strings (adapter, source, entity and metric ids, native units, and the provenance driver, device path and channel as `SharedText`) are interned per decoding thread (at most 8192 per type); `Scalar` decoding accepts either key order without buffering; the IPC structure pre-scan searches each string body once; the metric catalog lookup is indexed instead of scanned; and GPU process records are grouped in one pass with one GPU entity per UUID. | REF CPU budget (≤ 5 % of one logical core). Profiles showed allocation and copying of repeated strings and cloned records dominating the collector and Manager cost. PERFORMANCE.md §4 orders parse/batch work and caches before extra workers. The JSON shapes are unchanged and covered by the contract tests. | PERFORMANCE.md §2, §4, INTERFACES.md |
| D-32 | `DGXTOP_BENCH_SMOKE_SECONDS` (10–600, default 10) lengthens the REF smoke window for comparing changes. A smoke report is never acceptance evidence, whatever its length. | Ten-second windows had CPU noise larger than the effects being compared. Acceptance still needs `--full` (60 s warm-up + 1800 s, three runs). | PERFORMANCE.md §2 |
| D-33 | REF coverage counts a scheduled slot when a read of it finished inside the measurement window. The report is taken `COMMIT_GRACE_NS` (1 s) after the window ends, so a read that finished just before the end has time to commit; a read that commits later counts as missing. Window counters (drops, panics, restarts, diagnostics) are still taken at the window end. | A smoke run lost one slot of a 16-page group whose last cycle was still being collected when the report was taken at the window edge (99.84 % instead of 100 %). The denominator and the threshold are unchanged. | PERFORMANCE.md §2, AT28 |
| D-34 | Build provenance: a tree with modified or untracked files (ignored files excepted) reports `<commit>-dirty`, and the build script re-runs when any build input (`crates/`, `Cargo.toml`, `Cargo.lock`) or git's commit pointers (`HEAD`, index, the checked-out branch ref, `packed-refs`) change. | An unstaged edit or a new source file touched neither `.git/HEAD` nor the index, so a binary could carry a stale clean commit. Benchmark reports use this label to decide whether the source is identifiable. | OPERATIONS.md §5, AT20, AT37 |
| D-35 | A destructive request is bound to the authoritative selection, and the frame revision is checked when that selection is made. `UpdateViewSession` carries `frame_revision`: a click on a stale HitMap keeps the clicked identity and is rejected as StaleView when it no longer matches. `PrepareSignal` carries the full ProcessKey and is accepted only when it equals the Manager's current selection and the process is still listed (otherwise StaleView or ProcessExited); it is never retargeted to another row. | SECURITY.md §2 says PrepareSignal takes a frame_revision, and UI.md §3 says a destructive click from an old frame returns StaleView. But the closed `command.schema.json` has no frame_revision on PrepareSignal (`additionalProperties: false`). Binding the request to the frame-checked selection keeps the intent (a row index never becomes another process) without changing the schema. | SECURITY.md §2, UI.md §3, command.schema.json, AT11, AT13 |
| D-36 | Overview redesign requested by the owner (2026-10-05). (1) The overview leads with the GPUs: framed GPU cards in a grid (facts, utilization and memory gauges, activity line, utilization and temperature trends) take the largest share. (2) CPU, memory, disk and network are summaries side by side in one strip of at most 35 % of the body. CPU starts collapsed to its total; a click on the panel or `c` shows cores, load and sensors in a full-width band (presentation only, nothing is sent to the Manager). (3) Memory splits the RAM into what GPU processes hold on unified-memory GPUs (summed `gpu.memory.process_allocated`, counting only processes the driver lists), other use, page cache and free, each in its own color. A discrete GPU's VRAM is never counted as RAM. (4) The process table lists only processes with a GPU association, sizes itself by its rows, and is the only process UI: selection, sort, filter, GPU filter and `K` work in the overview. (5) The Sources and Processes tabs are no longer offered; the tabs are 1 Overview, 2 GPU, 3 History, 4 Settings, 5 Actions. Their modules and Manager views stay in the code so they can be restored. (6) The GPU view shows gauges beside grouped facts and side-by-side trends over the rest. Detail views show context lines only for topics their projection carries. | Direct owner feedback on the running program: the CPU panel hid everything else, GPU use matters most on a DGX, unified memory makes GPU RAM use important, and process work belongs on one screen. UI.md lists ten modules and a source diagnostics entry. Hiding the Sources view removes that entry from the interface (AT16's user path) by owner decision. | UI.md §1–§3, AT09, AT12, AT13, AT16 |
| D-37 | An adapter dispatch that a worker refuses (busy queue, ingress capacity, stopped worker) is a deferral, counted as `adapter_dispatch_deferred_total` with the reason `worker_busy`, `capacity` or `closed`, not as `queue_dropped_total`. The scheduler keeps the refused work pending and retries it after 20 ms. A slot the deferral makes a group miss is still recorded as a gap. The REF bench lists deferrals in its run details and keeps counting only real queue drops as unexplained drops. | A REF smoke run (2026-10-05, loaded desktop) counted one `queue_dropped_total{adapter_dispatch_refused}` as an unexplained drop while coverage stayed at 100 % (624 of 624 slots): nothing was dropped, the read went out on retry. The old label also hid which bound refused. `queue_dropped_total{bounded_reason}` counts dropped items, and the budget of 0 unexplained drops is unchanged. | OPERATIONS.md §3, PERFORMANCE.md §1, AT28 |

| D-41 | Overview histories are one-row sparklines beside their gauges (2026-10-08).
